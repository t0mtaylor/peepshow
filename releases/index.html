v0.9.3 — 2026-10-06

npm i -g peepshow@0.9.3

Fixed — peepshow was unusable on native Windows

Reported from outside in issue #3:

peepshow.CMD --version exited 1 with `The system cannot find the path

specified.before the CLI started, whilenode dist/cli.js` worked fine on

the same install. Two independent faults, each sufficient on its own, and

neither visible from a macOS or Linux CI run.

  • Every bin/ launcher was a #!/bin/sh script. npm and pnpm generate the Windows .CMD shim *from the target's shebang*, so all 93 commands shimmed to SET "_prog=/bin/sh" — a path that does not exist on Windows without Git Bash. All launchers are now bin/<name>.mjs with #!/usr/bin/env node, which shims to SET "_prog=node". Verified by generating real shims with npm's own cmd-shim for both shebangs and diffing the interpreter each selects.
  • 93 entry points would have silently no-opped anyway. Each sink decided whether to run via `import.meta.url ===file://${process.argv[1]}, which is false on Windows (file:///C:/…vsC:\…) *and* false through symlinks (/tmpvs/private/tmp). A false result means "I'm being imported", so the process would have exited 0 having done nothing. This is the same bug fixed forcli.ts` in 0.4.1; the fix never propagated. Now

Also in this area:

  • Launchers spawn the bundle rather than importing it, so argv[1] stays on the bundle and the guard above still works. bin/_launch.mjs is the shared helper: Node ≥ 22 check with the same exit 3 and message as before, nvm fallback when the running Node is too old, argv/stdio pass-through, exit code propagation, and signal forwarding so Ctrl-C reaches ffmpeg.
  • peepshow-sink-algolia, -otter and -typesense now actually install. They shipped launchers that were never registered in package.json bin, so npm i -g never put them on PATH. 93 commands → 96.
  • The slack and discord launchers keep their shell semantics exactly: the service-specific URL variable is aliased onto PEEPSHOW_WEBHOOK_URL only when the generic one is unset *or empty*, which a bare ?? would not reproduce. tests can import the helper under type-checked lint.

Verified by packing the tarball, installing it into a clean directory, and

running through node_modules/.bin/ — the symlink layer where the 0.4.1 bug

lived — including a real extraction end to end.

extensions, executable bits, bin-map parity, and the guard's behaviour through

symlinks and percent-encoded paths. They run on every platform, because that

is the only way a Mac notices a Windows packaging bug.

Changed — published docs and security policy

  • SECURITY.md — supported versions, private reporting via GitHub advisories, and an explicit account of what peepshow executes: ffmpeg resolution order and the PEEPSHOW_FFMPEG override, yt-dlp, sinks being arbitrary executables driven by ~/.peepshow/sinks.json, and serve binding loopback by default.
  • Placeholder credentials in the sink docs are now "<your-value>". Eleven docs used values shaped closely enough to real credentials ("patXXXXXXXX", "abcd-efgh-ijkl-mnop", "tk_abc123") that secret scanners flagged the documentation itself. Where the value is a real command the quotes are simply gone, since an assignment does not need them.
  • Both skills gained name: frontmatter.

Fixed — YouTube input was broken end to end

Three separate faults, each of which alone blocked every yt-dlp input

(local paths were never affected).

node:child_process with require() inside defaultSpawn(). Under

--experimental-strip-types the loader can't classify a .ts file that

contains both require and top-level await, so it refused the module on

evaluation — before the YouTube path was reached. The same require

survived into the esbuild ESM bundle, where dist/cli.js threw

Dynamic require of "node:child_process" is not supported. Replaced with a

static import; node:child_process is a builtin, so the lazy-load was

buying nothing. Test seams still inject through deps.spawn.

  • Format selector could never match. -f best[height<=720]… asks for a single file carrying both video and audio, and YouTube no longer publishes progressive formats for most uploads — everything is DASH, video-only plus audio-only. Every such video died with Requested format is not available. Now bv*[height<=720]+ba/b[height<=720]/bv*[height<=720]/b, with peepshow's own resolved ffmpeg passed via --ffmpeg-location so the merge works without an ffmpeg on the user's PATH. The protocol!^=m3u8 filter is gone — it removed valid fallbacks on HLS-only videos, and yt-dlp's default sort already prefers https.
  • Failures were opaque. yt-dlp's stderr was piped and then never read — so a failure surfaced as a bare yt-dlp failed (exit 1), and a chatty child could deadlock on a full pipe buffer. stderr is now drained, its tail quoted in the error, and a 403 (the classic stale-yt-dlp symptom) gets an explicit yt-dlp -U hint. Dropped --no-warnings: yt-dlp's own "outdated version" line now reaches the user via ResolvedInput.warnings even when the download succeeds.

already flagged the original call, but it was silenced inline, which is how

it shipped.

v0.8.1 — 2026-05-01

npm i -g peepshow@0.8.1

Added — sink replay (closes the v0.8.0 sink-log loop)

  • peepshow sinks log [--limit N] [--status ok|failed|skipped] — print recent sink interaction-log entries from ~/.peepshow/sink-log.ndjson. Default 20 newest, status-filterable.
  • peepshow sinks replay <logId> — re-pipe a past invocation. SinkReplayError with codes log_entry_not_found, manifest_missing, sink_spec_not_found, outputDir_missing. happy-path payload reconstruction (verifies the manifest's outputDir + strategy land in stdin).

v0.7.4 — 2026-04-27

npm i -g peepshow@0.7.4

Added — Perceptual frame dedup

  • --dedup on|auto|off (default on) — every extraction now runs an 8×8 dHash post-pass and drops frames whose hamming distance to the previous keeper is ≤ threshold. Catches the case ffmpeg's scene-detect misses (low-motion talking heads, slideshow recordings, security-cam loops) and stops fps-mode fallback from flooding the LLM with near-identical thumbnails. Single ffmpeg invocation hashes all frames in one pass — adds ~50–100ms for 40 frames on M1, well below typical extraction cost. auto runs only for fps fallback (since scene mode already filters); on covers both modes; off disables. --no-dedup is a shortcut for --dedup off.
  • --dedup-distance N (default 5, range 0..64) — hamming-distance threshold. 0 means only bit-identical hashes drop; higher = looser dedup. 5 is the sweet spot: tight enough to catch lighting flicker / duplicate slideshow frames, loose enough to keep legit minor scene changes.
  • Manifest schema (additive, still v1) — extraction.framesDeduped + extraction.dedupDistance fields surface what dedup did per run, so reports + sinks can show the count.
  • Soft-fail by design — if hashing throws (rare; only when ffmpeg can't decode our own JPEGs), extraction falls through to pruneToMax with the original frame list. Dedup is a quality pass, not a correctness gate.

Tests

  • 28 new unit tests across dHashFromBytes, hamming, selectKeepers, shouldDedup, computeDHashes (with stub spawn), applyDedup (real fs + collision-safe two-phase rename). extraction.* keys. addition.

Why we shipped this now

External feedback: *"Keyframes + transcript is a clean approach — most

'video understanding' demos cheat by relying purely on transcript.

Does it dedupe similar frames or just sample at fixed intervals?"*

Honest pre-fix answer was "scene mode kind of, fps fallback no."

Honest post-fix answer is "yes, perceptual dedup default-on for both

modes." Same pitch, no caveat.

Added — --gpu auto is now duration-aware

  • Short clips (<15s) auto-skip hwaccel under --gpu auto because videotoolbox / vaapi / d3d11va init overhead (~200-500ms) exceeds per-frame decode savings. Real measurements on the hero reel videos showed CPU 3-4× faster than GPU on 10-30s clips. The heuristic fixes this without changing the auto default — long/HD clips still get hardware decode.
  • Dual-axis threshold: <15s triggers CPU regardless of size; 15-30s also triggers CPU when height < 720p. >30s always uses the platform default. Both cutoffs are env-configurable: PEEPSHOW_GPU_MIN_SECONDS (default 15), PEEPSHOW_GPU_MIN_HEIGHT (default 720).
  • Explicit --gpu <backend> bypasses the heuristic — power users who want to force GPU just name the backend (--gpu videotoolbox, --gpu cuda, etc.). --gpu off still forces CPU. height × env override combination.

Added — Motion signal + adaptive density (high-motion answer)

  • extraction.motionSignalAvg + extraction.motionSignalLevel — average pairwise hamming distance across kept dHashes, classified as low (<6) · medium (<15) · high (15+). Free byproduct of dedup — the hashes were already computed. Surfaced in manifest.json so the consuming LLM can adjust its narration ("rapid motion segment...") and so reports can show "high motion · zero dups" rather than just "0 dropped".
  • High-motion stderr hint — when motion is high, dedup dropped 0 (every frame distinct), and framesEmitted ≤ 8, peepshow prints a one-line tip suggesting --fps 2 or a higher --max. Silent under PEEPSHOW_NO_HINTS=1.
  • --adaptive on|off (default on) — second-pass extraction. When dedup drops 0 frames AND motion is high AND framesEmitted < maxFrames * 0.6, peepshow re-extracts at higher fps to take advantage of the visual variety. Targets ~80% of --max on the second pass. Recursion is guarded — second pass forces adaptive: "off". --no-adaptive shortcuts disable. Verified live: synth high-motion clip went from 6 frames to 14 (2.3×) under the same --max budget.

Fixed — Scene-mode dedup was silently skipping

  • Scene extraction used -frame_pts 1 which named frames by their PTS (frame_0160.jpg, frame_0307.jpg …) rather than sequential. Dedup's ffmpeg pass globbed frame_%04d.jpg and found nothing on those runs, silently caught the failure, and returned dedupDistance: null. After this fix scene mode names sequentially again, dedup runs on every strategy, and the motion signal populates regardless of which path fired.

Tests

  • 8 new pure tests for averageAdjacentHamming + classifyMotion in
  • 8 new pure tests for shouldRunAdaptiveDensity covering every decision branch. extraction.* keys.

Added — sink storage modes

Database-shaped sinks (sqlite, postgres, mongodb) now support two

record layouts, chosen per-sink or globally:

  • multi (default) — the historical normalised layout: runs row + frame rows + tag rows.
  • single — one row / document per run carrying the entire SinkPayload (frames + audio + transcript) as a JSON blob (TEXT on SQLite, JSONB with GIN index on Postgres, native subdoc on Mongo). A few fields (duration, frames count) are promoted for cheap filtering without JSON parsing.

Precedence: PEEPSHOW_<SINK>_STORAGE_MODE env > PEEPSHOW_SINK_STORAGE_MODE

global env > a PEEPSHOW_SINK_CONFIG_FILE JSON file > the sink's own

fallback. Switching modes on an existing database is safe — the two

layouts live in parallel tables and nothing is migrated.

Full reference + query examples: [docs/SINK-STORAGE-MODES.md](./docs/SINK-STORAGE-MODES.md).

v0.4.1 — 2026-04-24

npm i -g peepshow@0.4.1

Emergency hotfix over 0.4.0. Three bugs stopped the published package from

running at all when installed via npm; none of them showed up in local dev

because everything in this repo runs via real paths under /Users/....

Fixed

  • Bin wrappers now work through node_modules/.bin symlinks. The 53 wrapper scripts (peepshow + 52 sink entries) resolved their own location with dirname "$0", which returns node_modules/.bin when invoked through npm's symlink — and the sibling _find-node.sh helper isn't there. Calling ./node_modules/.bin/peepshow (or any peepshow-sink-*) from a fresh install aborted with _find-node.sh: No such file or directory. Wrappers now resolve symlinks first so the helper is always found.
  • CLI no longer silently exits on macOS /tmp paths. The invokedDirectly guard compared import.meta.url to process.argv[1] as strings, but macOS resolves /tmp → /private/tmp on import.meta.url while argv[1] keeps the logical path. The compare always failed and the CLI returned 0 without doing anything. Both sides now go through realpathSync before comparison.
  • whisper.cpp transcripts populate again. The audio extraction step emits AAC-in-m4a, but whisper.cpp only accepts 16 kHz mono PCM WAV. runWhisperCpp now decodes the extracted audio via ffmpeg before invoking whisper-cli (matching the pattern the site reels builder already used). Previously every run reported skippedReason: "error: unable to parse whisper-cpp json" and no segments.

Added — audio extraction + transcription

When a video input has an audio stream (MP4 / MOV / WebM / MKV), peepshow

now runs a second ffmpeg pass that:

  • Extracts a compact mono 16 kHz AAC audio.m4a next to the frames.
  • Probes loudness peak (astats) + silence ratio (silencedetect).
  • Emits an audio field on the JSON payload with codec / duration / channels / sample rate / bitrate / peak / silence ratio.

On top of that, peepshow **auto-enables transcription when

whisper.cpp is on

PATH** — no flag, no API key, nothing leaves the machine. The

base.en model downloads once to ~/.peepshow/whisper-models/ and is

reused forever after. Explicit --no-transcribe or

PEEPSHOW_TRANSCRIBE=off skips the step.

Five cloud / custom providers are selectable in one flag:

  • --transcribe openai (needs OPENAI_API_KEY)
  • --transcribe groq (needs GROQ_API_KEY)
  • --transcribe deepgram (needs DEEPGRAM_API_KEY)
  • --transcribe assemblyai (needs ASSEMBLYAI_API_KEY)
  • --transcribe custom (needs PEEPSHOW_TRANSCRIBE_CMD)

Each cloud provider only runs when its API key env var is set — without

it, peepshow logs a one-line note and keeps the rest of the run intact.

The transcript lands on audio.transcript with the same shape across

every provider (provider, model, language, durationSeconds,

segments: [{start, end, text}], text), so downstream sinks see the

spoken words regardless of which engine produced them.

Full setup, provider matrix, and privacy notes:

peepshow.dev/transcription/.

Animated GIF, APNG, and animated WebP inputs skip cleanly — those

formats can't carry audio. Opt out entirely with --no-audio or

PEEPSHOW_AUDIO_ENCODER=off.
